# مدل عدم‌قطعیت (Uncertainty Model)

یک تصمیم معماری عرضی که در کل زنجیره اعمال می‌شود، نه یک ماژول مستقل.

## اصل
خروجی هیچ مرحله‌ای عدد قطعی نیست. تخمین بازه است، و هرجا داده کم باشد، **صریح
اعلام می‌شود** — نه اینکه بی‌صدا با فرض پر شود.

## سه منبع خطا و جای مدل‌سازی‌شان

| منبع خطا | کجا مدل می‌شود | چگونه به کاربر می‌رسد |
|---|---|---|
| تشخیص Scope | `SpaceObservation.confidence` (۰٫۷۵ صریح / ۰٫۴۵ فرضی) | فضاهای کم‌اطمینان قابل تأیید |
| قیمت بازار | `price_min`/`price_max` هر سطح متریال | بازهٔ هزینه در همهٔ خروجی‌ها |
| بهره‌وری و زمان | `DURATION_FACTOR_MIN/MAX` + `TIER_SPEED` | بازهٔ مدت اجرا |
| سربار پروژه | `OVERHEAD_MIN/MAX` (0.08–0.15) | داخل `cost_min`/`cost_max` |

## کانال اعلام فرض‌ها
`ScopeSummary.assumptions: list[str]` — هر فرضی که سامانه به‌جای کاربر کرده
(متراژ پیش‌فرض ۷۵ متر، عدم تشخیص وضعیت فضا، عدم نام‌بردن فضا، fallback تحلیل
بصری) به‌صورت جملهٔ فارسی ثبت و در بخش «فرض‌ها و محدودیت‌ها»ی Brief نمایش داده
می‌شود.

## دادهٔ ناقص، هرگز حذف بی‌صدا
- آیتم بدون قیمت → `missing` در `material.apply()` → `PipelineResult.missing_price_codes`
  → یادداشت در `Estimate.uncertainty_note` → قابل‌مشاهده در سند.
- خطای adapter بصری → fallback قاعده‌محور + جملهٔ «تحلیل بصری ناموفق بود».

## قواعد ثابت UX (از `docs/specs/ui-flow.md`)
۱. هیچ‌جا عدد قطعی هزینه نمایش داده نمی‌شود.
۲. فرض‌ها همیشه قابل‌مشاهده‌اند.
۳. خروجی خارج از دامنه رد می‌شود، نه با تخمین بی‌کیفیت.

## چرا این کار سختی‌تر از یک عدد است
نمایش یک عدد واحد، تصمیم کارفرما را قطعی جلوه می‌دهد و در اولین اختلاف با
مجری، اعتماد به کل سامانه از دست می‌رود. بازه + فرض شفاف، همان چیزی است که
مسئلهٔ اصلی README را هدف می‌گیرد: «قیمت غیرقابل‌مقایسه → اختلاف → اعتماد کم».
