# پروتکل تست پذیرش MVP (Issue #13)

> هدف: سنجش این‌که آیا خروجی MVP برای کارفرمایان واقعی قابل‌فهم و مفید است و
> آیا تخمین‌ها به quote واقعی مجری نزدیک است.
>
> **این سند ابزار می‌سازد؛ اجرای میدانی (یافتن پروژهٔ واقعی و مجری) کار انسان
> است.** معیارهای عددی در `docs/specs/mvp-scope-lock.md` قفل شده‌اند.

## ۱. نمونه‌گیری

- **حجم:** حداقل ۱۰ پروژهٔ واقعی (نه نمونهٔ ساختگی).
- **تنوع الزامی:** هر چهار فضای MVP حداقل دو بار حاضر باشند؛ حداقل سه پروژه
  تک‌فضا (مثل فقط سرویس) و دو پروژهٔ کامل واحد.
- **معیار ورود پروژه:** کارفرما بودجه و متراژ را اعلام کرده باشد و پروژه در
  آیندهٔ نزدیک به مجری سپرده شود (تا quote واقعی در دسترس باشد).

## ۲. گردش کار هر پروژه

```
۱. کارفرما پروژه را در سامانه ثبت می‌کند (عکس/ویدیو + متن + متراژ + بودجه)
۲. خروجی سامانه ثبت می‌شود: Scope + WBS + ۴ سناریو + Brief
۳. همان کارفرما Brief را برای حداقل ۲ مجری مستقل می‌فرستد
۴. quoteهای دریافتی ثبت می‌شوند
۵. مقایسه با معیارهای عددی انجام می‌شود
۶. کارفرما پرسش‌نامهٔ کیفی را پر می‌کند
```

**نکتهٔ حیاتی:** کارفرما و مجری نباید خروجی سامانه را دست‌کاری کنند. اگر مجری
فقط Brief را ببیند و بدون توضیح شفاهی قیمت بدهد، معیار «قابل‌فهم بودن» واقعاً
سنجیده شده است.

## ۳. محاسبهٔ معیارها

```
خطای هر پروژه = |تخمین − quote_میانه| / quote_میانه × ۱۰۰

quote_میانه = میانهٔ quoteهای مجریان آن پروژه
تخمین      = میانهٔ بازهٔ سناریوی انتخاب‌شده = (cost_min + cost_max) / ۲
```

اگر اختلاف quote دو مجری بیش از ۳۰٪ باشد، آن پروژه **برای سنجش خطای تخمین
نامعتبر** است (مبنا بی‌ثبات) ولی برای سنجش کیفی معتبر می‌ماند.

| معیار | آستانه | نتیجه |
|---|---|---|
| میانهٔ خطا | ≤ ۲۵٪ | ✅ قبول |
| بدترین مورد | ≤ ۵۰٪ | ✅ قبول |
| نرخ پوشش بازه | ≥ ۶۰٪ | ✅ قبول |
| ارزیابی کیفی «درست و قابل‌فهم» | ≥ ۷۰٪ | ✅ قبول |

**تصمیم ورود به فاز ۲:** اگر سه معیار از چهار معیار پاس شود، فاز ۲ (#14، #15)
فعال می‌شود. اگر خطای میانه بالای ۴۰٪ باشد، اول دیتاست قیمت (Issue #2)
کالیبره می‌شود، نه موتور AI.

## ۴. پرسش‌نامهٔ کیفی کارفرما

پس از مشاهدهٔ خروجی، با مقیاس ۱ (کاملاً مخالف) تا ۵ (کاملاً موافق):

1. فهمیدم سامانه دقیقاً چه کاری برای واحد من پیشنهاد می‌دهد.
2. ترتیب کارها (اول چه چیزی، بعد چه چیزی) برایم منطقی بود.
3. بازهٔ هزینه به واقعیت نزدیک بود.
4. متوجه شدم چرا قیمت یک بازه است و نه یک عدد.
5. اگر مجری‌ای قیمت متفاوتی بدهد، می‌توانم با این سند بحث کنم.
6. این خروجی را به یک دوست معرفی می‌کنم.
7. **باز:** کدام بخش سند را نفهمیدید؟ (پاسخ باز — مهم‌ترین سؤال)

**آستانهٔ قبولی:** میانگین پرسش‌های ۱ تا ۶ حداقل ۳.۵، و پرسش ۱ حداقل ۴.

## ۵. سنجش کیفیت Brief از دید مجری

سؤال کوتاه از هر مجری، **قبل** از دیدن پروژهٔ واقعی:

| سؤال | قبول |
|---|---|
| از این سند فهمیدید چه کاری باید انجام دهید؟ | بله/خیر |
| چیزی در سند مبهم بود؟ | پاسخ باز |
| برای قیمت‌دادن، سؤال اضافه‌ای از کارفرما پرسیدید؟ | بله/خیر — «خیر» هدف است |

**آستانه:** حداقل ۸۰٪ مجریان بگویند سؤال اضافه نپرسیدند (معیار پذیرش Issue #11).

## ۶. ثبت نتایج

نتایج در یک فایل گزارش در `outputs/acceptance-report.md` ثبت شود و شامل:

- جدول هر پروژه: متراژ، فضاها، تخمین، quoteها، خطا٪، داخل بازه (بله/خیر)
- میانگین و میانهٔ خطاها
- خلاصهٔ پاسخ‌های کیفی و نقل‌قول مستقیم کارفرمایان
- فهرست نقاط ضعف مشاهده‌شده و پیشنهاد اصلاح
- تصمیم نهایی: ورود به فاز ۲ یا بازگشت به کالیبراسیون

## ۷. خارج از دامنه
