# طراحی جریان کاربری — از آپلود تا Brief (Issue #12)

> این سند طراحی کامل جریان است. پیاده‌سازی UI در فاز بعد انجام می‌شود؛ منطق
> پشت آن (`app/pipeline.py`) آماده و تست‌شده است.

## ۱. نقشهٔ جریان

```
[۱] صفحهٔ شروع
      │  «قبل از شروع، پروژه‌ت رو بفهم.»
      ▼
[۲] فرم ورودی ──────────────────────────────┐
      │  عکس/ویدیو + توضیح + متراژ + بودجه   │ اعتبارسنجی ناموفق
      │  + سطح سلیقه                          │ → پیام خطای مشخص
      ▼                                       │   در همان فیلد
[۳] اعتبارسنجی ورودی ◄──────────────────────┘
      │  (متراژ ۲۰–۱۰۰۰، حداقل یک رسانه، حجم ≤ ۲۵MB)
      ▼
[۴] حالت پردازش (progress)
      │  مراحل: تحلیل فضا → تولید WBS → قیمت‌گذاری → تخمین
      ▼
[۵] نمایش ۴ سناریو (مقایسه کنار هم)
      │  اقتصادی | استاندارد | باکیفیت | مناسب اجاره
      ▼
[۶] جزئیات سناریوی انتخابی
      │  WBS با ترتیب اجرا + متریال هر آیتم + بازهٔ هزینه/زمان
      │  ← کاربر می‌تواند آیتم‌ها را ویرایش/حذف کند
      ▼
[۷] خروجی Brief (مشاهده → دانلود PDF → لینک اشتراک)
```

## ۲. هر صفحه چه چیزی نشان می‌دهد

### [۲] فرم ورودی
| فیلد | نوع | الزام | نکتهٔ UX |
|---|---|---|---|
| عکس/ویدیو | آپلود چندتایی | حداقل ۱ | کشیدن‌ورهاکردن + پیش‌نمایش بندانگشتی |
| توضیح متنی | textarea | توصیه‌شده | placeholder نمونه‌ای: «آشپزخانه قدیمیه، کابینت و کاشی عوض بشه» |
| متراژ | عددی | اختیاری | راهنما: «اگه نمی‌دونی، خالی بذار» |
| بودجه | عددی + واحد | اختیاری | واحد پیش‌فرض میلیون تومان |
| سبک | انتخاب از فهرست | اختیاری | مدرن / کلاسیک / اسکاندیناوی / لوکس |

### [۵] مقایسهٔ سناریوها
چهار کارت کنار هم (در موبایل: کشویی افقی)، هر کارت شامل:
- نام سناریو و یک جملهٔ توصیف
- **بازهٔ هزینه** (نه عدد قطعی) — درشت‌ترین عنصر کارت
- مدت اجرا به روز
- نشان «در بودجه» / «بالاتر از بودجه» اگر بودجه اعلام شده باشد
- دکمهٔ «انتخاب این سناریو»

### [۶] جزئیات سناریو
- جدول WBS گروه‌بندی‌شده بر اساس فاز، به‌ترتیب اجرا
- هر ردیف: شرح کار، فضا، مقدار + واحد، متریال پیشنهادی
- جمع هزینه در پایین، با تفکیک متریال/دستمزد
- ویرایش: حذف آیتم یا تغییر سطح متریال → تخمین بی‌درنگ بازمحاسبه می‌شود

### [۷] Brief
- پیش‌نمایش سند (همان HTML که `app/engines/brief.py` می‌سازد)
- دانلود PDF
- کپی لینک اشتراک

## ۳. حالت‌های خطا و ابهام

| وضعیت | رفتار سامانه | چرا |
|---|---|---|
| AI اطلاعات کافی ندارد | فضاهای نامطمئن با `confidence` پایین علامت‌گذاری و از کاربر تأیید گرفته می‌شود | تخمین روی فرض اشتباه، اعتماد را نابود می‌کند |
| فایلی که رد شد | پیام مشخص در همان فیلد («حجم فایل ۴۰MB است؛ حداکثر ۲۵MB») | کاربر باید بداند *چه* چیزی را عوض کند |
| تحلیل بصری ناموفق | تخمین از متن تولید می‌شود + یادداشت شفاف در بخش «فرض‌ها» | خروجی باید صادق باشد، نه بی‌صدا ناقص |
| آیتم بدون قیمت در دیتاست | کد آیتم در `missing_price_codes` و اعلام در سند | تخمین نباید عدد ناقص را کامل جلوه دهد |
| تخمین از بودجه بالاتر | نشان «بالاتر از بودجه» + پیشنهاد سناریوی ارزان‌تر | مسیر خروج به کاربر داده می‌شود، نه بن‌بست |
| درخواست خارج از دامنه (شهر دیگر، پروژهٔ تجاری) | پیام صریح «خارج از دامنهٔ فعلی» | تخمین بی‌کیفیت بدتر از نپذیرفتن است |

## ۴. قواعد ثابت تجربهٔ کاربری

1. **هیچ‌جا عدد قطعی هزینه نمایش داده نمی‌شود** — همیشه بازه. (اصل صداقت تخمین)
2. **فرض‌ها همیشه قابل‌مشاهده‌اند** — بخش «فرض‌ها و محدودیت‌ها» در Brief و در
   صفحهٔ نتایج.
3. **پیشرفت پردازش قابل‌مشاهده است** — پردازش چند ثانیه‌ای بدون نشانگر، حس
   خرابی می‌دهد.
4. **راست‌به‌چپ و فارسی در همهٔ حالت‌ها** — از جمله پیام‌های خطا.
5. **خروجی در هر مرحله قابل‌بازگشت است** — چون هر مرحلهٔ pipeline خروجی
   ساختاریافته دارد، کاربر می‌تواند بدون شروع از صفر ویرایش کند.

## ۵. خارج از دامنهٔ این طراحی

- ورود/ثبت‌نام و حساب کاربری (MVP بدون احراز هویت)
- اشتراک‌گذاری چندنفره و کامنت روی Brief
- اپلیکیشن موبایل مستقل
